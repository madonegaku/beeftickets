## Контекст

Відповідно до ADR-001 система будується як модульний моноліт. Потрібні: реляційна СУБД із транзакціями та обмеженнями цілісності (S3); швидкий HTTP API з підтримкою паралельних запитів (S1, S2); спосіб надійно виконувати фонові дії без окремих брокерів (S4); зручні автотести й навантажувальні тести; типізація та автоматична документація API.

Ключова умова: всі учасники команди повинні достатньо володіти обраним стеком для реалізації робіт 2–8.

### Вибір СУБД

Розглянуто PostgreSQL, MySQL та документну БД (MongoDB). Реляційна модель найприроднішою є для місць, резервів і замовлень із жорсткими зв’язками. PostgreSQL забезпечує транзакції, блокування рядків (`SELECT ... FOR UPDATE`, `SKIP LOCKED`), частково унікальні індекси, розвинені обмеження цілісності та тип JSONB для гнучких схем залів. Документна модель гірше відповідає вимозі суворої цілісності між зв’язаними сутностями.

## Рішення

Обрано **варіант 1**: Python, FastAPI та PostgreSQL. Вирішальні причини: спільна мова всієї команди; висока швидкодія API для I/O-навантаження, що відповідає S1–S2; PostgreSQL як єдине джерело істини для S3; автоматична специфікація OpenAPI, що спрощує узгодження інтерфейсів; мінімальний набір компонентів.

Додаткові рішення:

1. PostgreSQL є єдиним сховищем стану; окремі кеші та брокери повідомлень не використовуються, кеш каталогу зберігається в пам’яті процесу з обмеженим часом життя.
2. Схема БД змінюється лише через міграції Alembic.
3. Фонові дії виконуються засобами FastAPI та asyncio, а їхні наміри зберігаються в таблиці `outbox`; обробка webhook платіжного провайдера спершу зберігає подію в БД і є ідемпотентною.
4. Середовище розробки та запуску описується в Docker Compose (застосунок і PostgreSQL); якість коду контролюється ruff, mypy та pre-commit.

Склад стека: Python 3.12+, FastAPI (Pydantic, Uvicorn), SQLAlchemy 2.x, Alembic, PostgreSQL 16+, JWT, pytest, Locust, Docker, Docker Compose, ruff, mypy, pre-commit.

## Наслідки

### Позитивні

- єдина мова на всьому бекенді знижує поріг входу та полегшує ротацію ролей;
- мінімум компонентів спрощує розгортання та налагодження;
- автогенерація OpenAPI та типізація зменшують кількість помилок інтеграції;
- транзакційні можливості PostgreSQL дозволяють доводити виконання S3 навантажувальним тестом.

### Негативні

- більше компонентів збирається вручну (автентифікація, адміністрування) порівняно з Django;
- необхідна дисципліна у виборі між синхронним та асинхронним доступом до БД;
- без брокера фонові дії виконуються в процесі застосунку, тому їхня надійність залежить від `outbox` і повторних спроб;
- кеш і обмеження частоти запитів діють на рівні одного екземпляра;
- залежність від якості та підтримки сторонніх бібліотек.

### Технічний борг і умови перегляду

Адміністративна панель для підтримки та модерації відкладається. Рішення переглядається, якщо самооцінка команди виявить недостатнє володіння ключовою технологією, якщо цільові міри продуктивності не досягаються на цьому стеку або якщо виникне потреба в окремих воркерах чи спільному кеші (тоді додається новий ADR, який замінює цей).
